# V0.2 — Intelligent functional testing

This release extends V0.1 without replacing its CLI, project storage, repository analysis, hybrid analysis or execution history. Offline discovery is passive. Functional interactions run only after the operator supplies an evidence-grounded behavior contract and approves the corresponding scenario. Unknown outcomes remain manual review items.

## Discovery and evidence

`observation.py` records semantic roles and names, relevant non-value attributes, required/type/min/max/pattern constraints, select options, form association, timestamps and screenshot references. Locator candidates use role, label, placeholder or observed data-testid values. Counts are checked through actual Playwright locators. Functional actions require a candidate that matched exactly one element at discovery; ambiguous controls are rejected. Result collection assertions can use checked repeated locators. No CSS selector for either demo or the external target is embedded in the generator.

Passive taxonomy recognizes search fields/buttons, forms and required fields, common category/filter controls, sort controls, article/content cards, navigation, checkbox/radio/select controls, status/alert/live regions, potential empty states and loading signals. Some classifications are heuristics and remain INFERRED. Hidden elements with semantic/test-id evidence may be retained for later empty-state assertions. Counts describe checked DOM matches, not a permanent guarantee of runtime uniqueness.

`discovery/workflow-map.json` retains page relationships and structured evidence records. Categories include OBSERVED, SOURCE, VERIFIED_REQUIREMENT, INFERRED and UNKNOWN. Imported requirements record their declared human/fixture source separately. A declaration is not an independently verified business specification. Approval remains mandatory.

## Reviewed behavior contracts

Discover first, inspect saved controls and evidence IDs, then author a JSON array. Importing does not approve it:

```powershell
uv run autoqa plan --requirements .\reviewed-behavior.json --project projects\CLIENT
uv run autoqa plan --approve TC-F-search-found --project projects\CLIENT
uv run autoqa generate --approved --project projects\CLIENT
uv run autoqa run --project projects\CLIENT
```

The following is a schema illustration. Replace every example ID, URL and expectation with actual observed evidence and an authorized requirement; it cannot be run as-is:

```json
[
  {
    "id": "search-found",
    "title": "Search returns the approved matching item",
    "page_url": "http://127.0.0.1:8001/inventory",
    "workflow": "search",
    "test_type": "Positive",
    "basis": "VERIFIED_REQUIREMENT",
    "source": "Approved fixture requirement or authorized specification reference",
    "evidence_ids": ["EL-OBSERVED-SEARCH", "EL-OBSERVED-RESULTS"],
    "steps": [{"action": "fill", "element_id": "EL-OBSERVED-SEARCH", "value": "Approved query"}],
    "assertions": [{"check": "texts", "element_id": "EL-OBSERVED-RESULTS", "expected": ["Approved result title"]}],
    "test_data": {"query": "Approved query"},
    "allow_submit": false
  }
]
```

Workflow types: search, filter, sorting, form and product. Test polarity: Positive, Negative, Boundary, Regression or End-to-End. Inferred search/form workflows automatically produce positive and negative **manual** proposals until expectations are supplied. Filtering/sorting proposals also remain manual without a verified outcome. There are no fabricated API or boundary rules.

Actions: fill, select, check, uncheck and limited button click. Assertions: exact text list, count, text, visible/hidden, native field validity properties and numeric ordering. Required/email/minimum tests assert observed HTML constraint semantics rather than invented localized error messages. Ordering requires an explicit item count and numeric text; arbitrary locale/currency formats and asynchronous reordering remain limitations. Exact ordered names can be supplied as an additional auto-waited assertion.

Selections must match observed options. Unknown evidence, unsupported actions, missing/ambiguous action locators, credential fields, dangerous controls and generic visibility-only search/filter/sort expectations are rejected. Non-search button clicks require `allow_submit: true` and a controlled loopback target; all network writes remain blocked even there. Native validation and local JavaScript success responses are supported; arbitrary external form submission is not.

Contracts persist in test-cases/behavior-contracts.json. Approvals and rejections persist across CLI processes. Replanning preserves a decision only for unchanged scenario content. Changed evidence/expectations reset approval. Reimport contracts after a new discovery changes element IDs. `plan --reject ID` records rejection without deleting the case.

## Generation and execution

`functional.py` renders data through fixed Python templates. It never evaluates application/model text as Python. Generated tests use checked semantic locators, exact result assertions, Playwright waiting and fresh browser contexts. Product navigation links are grounded in their observed destinations and headings; the local benchmark selects a link whose product name matches the observed detail heading. No site-specific product names or routes are built into the generator.

Before execution: AST syntax validation, Ruff formatting/lint checks, manifest/approval checks and a separate Pytest collection pass. The environment is restricted to selected OS variables and controlled execution settings; ambient Pytest plugins/configuration are excluded. This is trusted-template process isolation, **not** an OS sandbox. Untrusted AI-generated/client Python is never accepted for execution. Do not bypass integrity checks or execute arbitrary code in client environments.

Runs retain JUnit, JSON, collection logs, pytest logs, screenshots and traces. V0.2 adds scenario/planning/discovery snapshots so later planning edits cannot rewrite historical report metrics. V0.1 records without snapshots use compatible fallback behavior. Existing V0.1 templates/approvals are supported; no historical artifacts were deleted.

## Diagnostics and reports

Diagnostics distinguish ambiguity, missing locators, timeouts, unexpected navigation, functional result mismatches, native validation failures and environment symptoms. They expose expected/observed behavior, actual error, evidence, advice and uncertainty. Categories identify TEST AUTOMATION FAILURE, APPLICATION DEFECT CANDIDATE, ENVIRONMENT FAILURE or UNKNOWN. A candidate is not a confirmed root cause. No repairs or assertion weakening occur.

Reports use recorded counts for pages, interactive controls, workflows, proposed/approved/pending/rejected scenarios, generated/executed results, functional passes and potential defects. Results are grouped by workflow/feature. Unverified scenarios and recommendations are explicit. HTML is escaped, and screenshots/traces/logs remain available. Requirements coverage is never calculated without a baseline.

## AI status

The existing optional official SDK provider now supports typed positive/negative/boundary suggestions, proposed data and behavioral assertion ideas. These stay REQUIRES_REVIEW, reference known workflow IDs and never become verified facts, approvals or executable code. Unknown IDs are rejected. Offline outputs are explicitly deterministic.

Normal tests mock the provider. The live integration test is skipped unless explicitly enabled with AUTOQA_LIVE_AI=1 plus OPENAI_API_KEY, AUTOQA_AI_MODEL and the optional SDK. It sends only synthetic evidence. No live AI success is claimed.

```powershell
uv sync --locked --extra ai
# Set OPENAI_API_KEY through your secret manager; never paste it into code/logs.
$env:AUTOQA_AI_MODEL = 'YOUR_STRUCTURED_OUTPUT_MODEL'
$env:AUTOQA_LIVE_AI = '1'
uv run --extra ai pytest tests\test_live_ai.py -q
Remove-Item Env:AUTOQA_LIVE_AI
```

## External validation and current limits

External acceptance evidence is isolated in projects/toolshop-v02. Published robots.txt identifies a test-automation learning platform, allows the root, and excludes /account, /admin, /auth and /checkout. Those prefixes are recorded in the project's excluded_paths scope configuration. The official project describes an Angular testing practice application: https://github.com/testsmith-io/practice-software-testing. No test code, selectors, routes, product data or assertions were copied.

The external attempt retains max_pages 8, max_depth 2, one browser page and 500 ms permitted-request spacing. Same-origin restrictions, query URL restrictions, DNS validation, network-write blocking and access controls remain enforced. External results are recorded separately in docs/v02-external-validation.json and the final verification addendum. A blocked resource or missing functional evidence is a limitation, not a product defect or a passing test.

Known remaining limits: only semantic role/label/placeholder/test-id locators; finite heuristic classification; manual requirement/data review; no arbitrary CSS selectors or general action scripting; no cross-page functional action chains beyond observed navigation; no authentication; no arbitrary private network access; no remote repository writes; no AI Python execution; cooperative exploration timeout and incomplete Windows descendant cleanup on forced termination. Initial discovery does not probe dynamic outcomes. Contracts explicitly supply known expected behavior before an approved interaction.
